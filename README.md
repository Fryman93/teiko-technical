# Loblaw Bio — Miraclib Immune Cell Analysis

Report on Bob Loblaw's clinical trial, exploring whether certain immune cell population frequencies predict melanoma patients' response to the drug **miraclib**.

---

## 1. How to Run

Set the project root as your working directory, then run the three commands below in the following order:

| Command | What it does |
|---|---|
| `make setup` | Creates `venv/` and installs every package pinned in `requirements.txt`. |
| `make pipeline` | Runs `load_data.py` (builds `loblaw.db` from `cell-count.csv`), then `analysis.py`, writing the relevant tables and figures to `outputs/`. |
| `make dashboard` | Starts a local Streamlit server outputting the contents of `outputs/`. |

## 2. Database Schema

Three tables:

```
  SUBJECTS {
    text subject PK
    text project
    text condition
    int age
    text sex
    text treatment
    text response
  }
  SAMPLES {
    text sample PK
    text subject FK
    text sample_type
    int time_from_treatment_start
  }
  CELL_COUNTS {
    int id PK
    text sample FK
    text population
    int count
  }
```

- **`subjects`** — one row per patient. Everything that's true about the *person*
  regardless of how many samples they contribute (project, condition,
  basic demographics, treatment, response).
- **`samples`** — one row per biological sample. Everything specific to *that
  draw* (sample type, timepoint).
- **`cell_counts`** — one row per sample-population pair. The count for a
  single immune cell population in a single sample.

### Rationale

A patient contributes multiple samples (one per timepoint), and each
sample has counts across five cell populations. With this schema, 
Subject-level data can live in `subjects`, without being repeated on every 
sample since they do not change between their respective samples.

In addition, the cell population counts data in their native format are stored in their own columns, which can become problematic with scaling because adding new cell populations would require changing the columns, hence the whole schema. With `cell_counts`, not only can novel cell types be easily included with the `population` column, but querying will be made much simpler since the all counts are now saved to a single column `count`.

### How this could scale further

This current design would remove scaling constraints for cell populations with the `cell_counts` table. It is worth noting however that as sample count grows into the thousands, `cell_counts` grows multiplicatively rather than linearly (multiple cell populations per sample). Adding indexes on `cell_counts.sample` and other frequently filtered columns (`condition`, `treatment`, `time_from_treatment_start`) would keep joins and aggregations efficient at that scale.

In order to comfortably support hundreds of projects, a `projects` table could be implemented in the schema to handle project-level metadata. 

To handle a broader range of analytics, an `analytics` table could be introduced that would reference the types of analytics done, start and end dates, key results, and of course, which samples were used in the analysis.

## 3. Code Structure and Explanation

```
.
├── Makefile              # orchestration: setup / pipeline / dashboard
├── README.md
├── requirements.txt      # pinned dependencies
├── load_data.py          # Part 1 — schema + data load
├── analysis.py           # Parts 2–4 — all analysis, saves outputs/
├── dashboard.py          # Streamlit dashboard — reads outputs/, no analysis logic
├── cell-count.csv        # raw dataset (provided)
├── loblaw.db              # generated by load_data.py
└── outputs/               # generated by analysis.py
    ├── pt2_initial_analysis.csv
    ├── pt3_compare_cell_pop.csv
    ├── pt3_shapiro_results.csv
    ├── pt3_sig_results.csv
    ├── pt3_cell_box_plots.png
    ├── pt3_cell_dist_plots.png
    ├── pt4_num_samples_per_prj.csv
    ├── pt4_num_responders.csv
    └──pt4_num_gender.csv
```


- `sqlite` and `pandas` were used to initiate the database and handle all
  transformations of the
  data, `seaborn` was used to create all the visualizations, and lastly, `streamlit` was implemented to
  generate the dashboard with the results.

- `analysis.py` writes the results to `outputs/`, and `dashboard.py` only 
  reads those files back in and
  outputs them. This means the dashboard loads instantly (no recomputation on every page load), the analysis can be rerun independently of whether anyone's viewing the dashboard, and each script has a single, clear responsibility.

- **Statistical tests use both Mann-Whitney U and Welch's t-test** (see
  `pt3_sig_results.csv`) rather than picking one test per population
  based on its individual normality result. Since Shapiro-Wilk results were
  mixed across the five populations, reporting both tests side by side is
  a more robust and consistent methodology, and gives a stronger confidence in 
  the result if both tests agree.

## 4. Dashboard

The dashboard is built with [Streamlit](https://streamlit.io) and renders the
outputs of `analysis.py` across three tabs (Part 2, Part 3, Part 4).

- **Local:** `make dashboard`, then open the URL Streamlit prints
  (usually `http://localhost:8501`).
- **Deployed:** https://bob-boblaw.streamlit.app/
